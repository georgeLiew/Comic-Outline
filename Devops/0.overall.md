# 《DevOps：今晚又不能下班了》
故事背景

公司：GoTicket

业务：巴士、火车、Taxi、Airport Transfer 售票平台。

主要角色：

👨‍💼 老板 David：只关心「为什么 Production 又挂了？」
👨‍💻 Developer 阿明：经典台词：「我电脑可以啊。」
🧑‍🔧 Ops Jack：负责 Server，每次 Deployment 最紧张的人。
👩‍💼 PM Sarah：每天问：「几时可以 Deploy？」
🧪 QA Mei：最怕 Developer 星期五下午突然要求上线。
🧙 DevOps Engineer Ken：后期登场，开始改变整个团队。

## Chapter 1：为什么我的电脑可以，Production 不可以？
案例：星期五晚上 6:00

阿明：

「Taxi Booking 新版本做好了，我这里测试全部 Pass。」

PM：

「很好！今天上线！」

Jack：

「你把文件 ZIP 给我。」

阿明把：

TaxiBooking_Final_Final_v3.zip

丢给 Jack。

Jack 手动：

复制文件 → RDP Server → Backup → Stop IIS → Replace File → 修改 config → Start IIS。

结果：

Production 500 Internal Server Error

老板：

「刚才不是说 Test 过了吗？！」

阿明：

「我电脑真的可以……」

Jack：

「Production 的 .NET Runtime 跟你电脑不一样！」

漫画冲突

大家开始互相指责。

Developer：

「Server configuration 是 Ops 的问题。」

Ops：

「你们 Developer 每次丢一个 ZIP 给我，我哪里知道需要什么？」

这时候 DevOps Engineer Ken 第一次出现：

「问题可能不是谁做错了。」

「而是 Development 和 Operations 根本是两个世界。」

最后才解释

这就是 DevOps 要解决的第一个问题：Development 与 Operations 的隔离。

传统：

Developer → ZIP → Ops → Production

DevOps：

Code → Build → Test → Package → Deploy → Monitor

操作篇

这一章最后才教：

Git Repository
Branch
Commit
Pull Request
Build Artifact
Environment Configuration
Development / Staging / Production 区别

## Chapter 2：到底是谁改坏 Production？
案例

星期一早上。

Customer Service：

「Airport Transfer 不能付款！」

Jack：

「昨天没有 Deploy 啊。」

阿明：

「我也没有 Deploy。」

大家开始调查。

最后发现某个 Developer 星期日晚上直接进入 Production Server：

把：

PaymentTimeout = 30

改成：

PaymentTimeout = 3

因为他想测试 timeout。

但是——

没有人知道是谁改的。

老板：

「Production 为什么任何人都可以进去改东西？！」

问题

团队没有：

Version Control
Change History
Approval
Audit Trail

Ken：

「如果 Production 的状态只能靠人的记忆，我们永远不知道昨天发生了什么。」

最后解释

引出：

Git + Version Control

漫画展示：

main
 │
 ├── feature/payment
 │
 ├── bugfix/taxi-price
 │
 └── feature/new-booking

所有改变必须：

Change → Commit → Pull Request → Review → Merge

操作篇

最后才实际教：

git clone
git checkout -b
git add
git commit
git push
git pull
git merge

以及：

Git Flow
Feature Branch
Pull Request
Code Review
Tag / Release

## Chapter 3：为什么每次 Deployment 都像拆炸弹？
案例

公司每个月 Release 一次。

Deployment Checklist：

1. Backup folder
2. Stop IIS
3. Copy DLL
4. Copy config
5. Run SQL script
6. Restart IIS
7. Test login
8. Test booking

Jack 拿着 Checklist 一项一项做。

这次他漏了：

Step 5：Run SQL Script

Application 新版本已经期待：

Booking.PaymentStatus

但是 Production Database 没有这个 Column。

结果：

💥 Production Crash。

老板：

「为什么部署一定要靠一个人记得十几个步骤？」

最后解释

Ken 在白板写：

「如果每次都做一样的事情，就不应该让人重复做。」

引出：

CI/CD

CI = Continuous Integration

Developer 每次 Push：

Push → Build → Unit Test → Package

CD = Continuous Delivery / Deployment

Artifact → Staging → Test → Approval → Production

操作篇

介绍 Pipeline：

Developer
   ↓
Git
   ↓
Build
   ↓
Unit Test
   ↓
Artifact
   ↓
Deploy Staging
   ↓
Integration Test
   ↓
Approval
   ↓
Production

再介绍常见工具：

GitHub Actions
GitLab CI/CD
Jenkins
Azure DevOps Pipeline

## Chapter 4：Production Server 到底装了什么？

公司现在有：

UAT Server

.NET 8.0.7

Production 2：

.NET 8.0.3

而且一个 Server 安装了额外 dependency。

「你们所谓的『一样』，只是人觉得一样。」

最后解释

引出：

Infrastructure as Code（IaC）

不要：

Jack 手动建立 Server。

而是：

Server Configuration = Code

例如：

CPU
Memory
Network
Firewall
Runtime
Database
Load Balancer

全部由 Code 定义。

操作篇

介绍：

Terraform
Ansible
ARM / Bicep
Infrastructure as Code
Immutable Infrastructure

概念：

terraform plan
      ↓
terraform apply
      ↓
Infrastructure

## Chapter 13：DevOps 到底有没有让公司变好？

最后老板问：

「我们买了 Kubernetes、Docker、Grafana、Azure DevOps……」

「所以 DevOps 成功了吗？」

Ken：

「工具装完，不代表 DevOps 成功。」

老板：

「那怎样衡量？」

最后揭晓 DORA Metrics

DevOps 最终不是看：

「我们用了多少工具。」

而是看软件交付能力。

四个重要指标：

Deployment Frequency
多久 Deploy 一次？

Lead Time for Changes
Commit 到 Production 要多久？

Change Failure Rate
多少 Deployment 导致 Production Failure？

Mean Time to Restore（MTTR）
出问题后多久恢复？

于是老板看到：

以前


Deploy：1次 / Month
Lead Time：14 Days
Failure Rate：30%
Recovery：4 Hours




现在


Deploy：10次 / Week
Lead Time：2 Hours
Failure Rate：5%
Recovery：15 Minutes

老板：

「原来 DevOps 不是为了让 Developer Deploy 更快。」

Ken：

「是让公司可以——」

更快、更安全、更稳定地改变 Production。
