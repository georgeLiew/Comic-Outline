# 《1-on-1 不是问“最近还好吗？”》

## Software Development Manager 实战漫画

这一章专门讲 **SDM 怎么做真正有价值的 1-on-1**。

主角继续是刚从 Tech Lead 升上 Software Development Manager 的 **Alex**。

他以前以为：

> 1-on-1 = 跟 Developer 聊聊天，看看有没有问题。

后来才发现，一场好的 1-on-1，其实至少要持续观察五件事：

**Performance → Career → Workload → Problem → Action**

而且这五件事经常是连在一起的。

---

# Chapter：为什么每次 1-on-1 都说“没问题”，最后却真的出问题？

## 案例

星期三，2:00 PM。

Alex 跟 Senior Developer Ben 有一个 30 分钟的 1-on-1。

Alex 打开 Teams。

**Alex：**

「最近怎么样？」

**Ben：**

「OK 啊。」

**Alex：**

「Project 呢？」

**Ben：**

「也是 OK。」

**Alex：**

「有什么 Problem 吗？」

**Ben：**

「暂时没有。」

Alex看了一下时间。

2:07 PM。

不知道要聊什么了。

于是他说：

「OK，有什么问题再找我。」

1-on-1 结束。

Alex觉得：

> Ben 是 Senior，应该不用太担心。

---

# 两个月后

事情开始不对劲。

Ben负责的 Payment Module 连续两个 Sprint Delay。

Code Review 越来越慢。

Junior Developer 问问题时，Ben开始回复：

> 「你先自己看。」

Production Issue 出现以后，Ben明显很烦躁。

有一天 Product Owner 问：

**PO：**

「为什么 Payment Integration 又 Delay？」

Alex开始检查。

结果发现 Ben 手上同时有：

* Payment Integration
* Production Support
* Junior Mentoring
* Architecture Discussion
* Code Review
* Legacy System Bug
* Customer Technical Meeting

Alex问：

**Alex：**

「为什么你没有告诉我 Workload 已经这么高？」

Ben沉默了一下。

然后说：

**Ben：**

「我之前有想过讲。」

「可是每次 1-on-1 你都问我有没有 Problem。」

「我也不知道这个算不算 Problem。」

Alex这时候才发现：

> **“Any problem?” 是一个非常差的 1-on-1 问题。**

因为 Developer 通常不会主动把真正的问题分类好，再交给 Manager。

Manager 必须主动去发现。

---

# Alex重新设计 1-on-1

从下一次开始，他把 1-on-1 分成五个区域：

| Area        | Manager 想知道什么                |
| ----------- | ---------------------------- |
| Performance | 这个人现在表现怎么样？                  |
| Career      | 他想去哪里？                       |
| Workload    | 他现在是不是 Overload / Underload？ |
| Problem     | 什么东西正在阻碍他？                   |
| Action      | Manager 接下来要做什么？             |

---

# Part 1：Performance

下一次 1-on-1。

Alex没有问：

> 「Performance OK吗？」

而是问：

**Alex：**

「过去两个 Sprint，你觉得自己做得最好的一件事情是什么？」

Ben想了一下。

**Ben：**

「Payment Retry Mechanism。我觉得 Design 做得不错。」

Alex继续问：

「如果有一件事情你觉得自己可以做得更好，会是什么？」

Ben：

「可能 Code Review。」

「最近真的很多东西，所以我通常只是看有没有明显问题。」

这个答案马上暴露出一个 Signal。

Alex继续：

「我也注意到最近几个 PR Review 花比较久。」

「你觉得是 Skill Problem、Priority Problem，还是 Time Problem？」

Ben：

「Time。」

这时候 Alex 没有马上判断：

> Ben Performance 不好。

因为：

**Performance Issue ≠ 一定是 Capability Issue。**

可能是：

**Performance = Capability × Clarity × Capacity × Motivation**

Ben可能有能力。

但是 Capacity 已经不足。

---

# Performance 到底看什么？

Alex开始固定观察几个维度：

### Delivery

答应的东西有没有完成？

例如：

* Sprint Commitment
* Feature Delivery
* Bug Resolution
* Deadline

### Quality

交出来的东西质量如何？

例如：

* Production Defect
* Rework
* Code Quality
* Test Coverage
* Technical Debt

### Ownership

遇到问题的时候，是：

> 「这个不是我的问题。」

还是：

> 「我先看看怎么解决。」

### Collaboration

能不能：

* 跟 QA 合作
* 跟 PO Clarify Requirement
* Mentor Junior
* 做 Code Review
* 分享 Knowledge

### Growth

同样的问题是不是不断重复？

还是每几个月都可以看到能力提升？

---

# 但 Alex 学到一个重要原则

**1-on-1 不是 Performance Review Meeting。**

不要每两个星期突然给 Developer 打分：

> Delivery：3/5
> Quality：4/5
> Communication：2/5

这样 Developer 很快就不会跟你说真话。

1-on-1 的目的应该是：

> **尽早发现 Performance Signal。**

真正正式的 Rating 可以放在 Performance Review。

---

# Part 2：Career

Alex以前几乎不会问 Career。

因为他觉得：

> Developer 的 Career 不就是 Junior → Senior → Lead 吗？

直到他问 Ben：

**Alex：**

「如果两年后你还在这个 Team，你希望自己在做什么？」

Ben：

「其实……我不太想做 Team Lead。」

Alex愣了一下。

因为他原本已经计划：

> 明年让 Ben 接 Team Lead。

Alex：

「那你想走什么方向？」

Ben：

「Architecture。」

「我比较喜欢 System Design、Performance、Integration。」

这一个问题直接改变了 Alex 对 Ben 的 Development Plan。

---

# Career 不是问：

> 「你想升职吗？」

因为几乎所有人都会说：

> 「想。」

真正应该问的是：

### Direction

「未来 1–2 年，你比较想往哪个方向发展？」

例如：

**Technical Path**

Developer
↓
Senior
↓
Staff / Principal / Architect

或者：

**Management Path**

Developer
↓
Senior
↓
Team Lead
↓
Engineering Manager

---

# Career 还要问 Gap

Alex：

「如果你想往 Architecture 走，你觉得自己现在缺什么？」

Ben：

「Cloud Architecture。」

「还有大型 System Integration。」

于是 Career Discussion 开始变成实际计划。

不是：

> “以后给你机会。”

而是：

> **Career Goal → Skill Gap → Opportunity → Action**

例如：

**Goal**

Solution Architect

↓

**Gap**

Cloud Architecture

↓

**Opportunity**

让 Ben 参与下一个 Azure Migration Project

↓

**Action**

让 Ben负责：

* Architecture Diagram
* Capacity Planning
* Integration Design
* Architecture Review

这才叫 Career Development。

---

# Part 3：Workload

接下来 Alex 开始画 Ben 的工作。

Ben说：

「我现在主要做 Payment。」

Alex没有接受这个答案。

他继续问：

「除了 Payment，还有什么事情会吃掉你的时间？」

慢慢地，清单变成：

| Work               | Approx. Capacity |
| ------------------ | ---------------: |
| Payment Project    |              50% |
| Production Support |              20% |
| Code Review        |              10% |
| Junior Support     |              15% |
| Meeting            |              15% |

Total：

**110%**

而且还没有算突发 Production Issue。

Alex终于知道为什么 Ben 一直 Delay。

---

# Manager 最危险的误判

看到 Delay：

> 「Developer Productivity 不够。」

但真正的问题可能是：

> **Developer Capacity 已经超过 100%。**

所以 1-on-1 必须问：

「现在什么事情最占你的时间？」

「有什么工作是别人不知道你正在做的？」

「如果明天再给你一个 Urgent Task，你会 Drop 哪一个？」

最后这个问题特别重要。

因为如果 Developer 回答：

> 「不知道。」

通常代表：

**Priority 不清楚。**

如果他说：

> 「没有东西可以 Drop。」

通常代表：

**Capacity 已满。**

---

# Part 4：Problem

接下来才进入 Problem。

但 Alex 不再问：

> 「Any problem？」

他开始把 Problem 拆开。

---

## Problem 1：Technical

「最近有什么 Technical Problem 一直卡着你？」

例如：

* Legacy Code
* Database Performance
* Architecture
* Environment
* Deployment
* Dependency

---

## Problem 2：Requirement

「有没有 Requirement 是你觉得不清楚，但 Team 还是继续做？」

这个问题经常会发现：

Developer 其实已经知道 Requirement 有问题。

只是没有人 Stop。

---

## Problem 3：Process

「有没有什么 Process 让你觉得一直浪费时间？」

可能出现：

> 每次 Deploy 都要手动做 20 个 Step。

或者：

> QA Environment 每星期坏两次。

这时候问题已经不是 Developer Productivity。

而是：

**Engineering System Productivity。**

---

## Problem 4：People

这个通常最难问。

Alex不会直接问：

> 「你跟谁关系不好？」

而是问：

「最近跟其他 Team Collaboration 顺吗？」

Ben沉默了一下。

「其实……我跟 Jason 合作有一点困难。」

Alex：

「发生什么？」

Ben：

「他每次 Requirement 没 Confirm 就叫我们 Start。」

现在 Alex发现：

表面上是 Developer Delay。

底层其实可能是：

> Requirement Management Problem。

---

# Part 5：Manager Problem

Alex最后增加了一个以前从来没有问过的问题：

**Alex：**

「有没有什么事情，是我作为 Manager 可以做得更好的？」

Ben笑了一下。

「真的可以讲？」

Alex：

「可以。」

Ben：

「有时候你会直接答应 Management 的 Deadline。」

「然后回来才问我们做不做得到。」

Alex沉默了。

这一刻非常重要。

因为：

**1-on-1 不只是 Manager Review Developer。**

也是 Developer 给 Manager Feedback 的地方。

如果 Developer 永远只说：

> 「你做得很好。」

不一定代表 Manager 很好。

也可能代表：

> **Psychological Safety 不够。**

---

# Part 6：Action

很多 Manager 的 1-on-1 到这里就结束。

聊了很多。

然后：

什么都没有发生。

这是另一个大问题。

所以 Alex最后固定问：

> 「今天聊的事情里面，有什么需要我 Follow Up？」

Ben这次有三个：

### Action 1

Production Support Rotation 调整。

Owner：Alex

### Action 2

让 Ben 参与 Azure Architecture Project。

Owner：Alex

### Action 3

Ben整理目前 Payment Project 的 Architecture Gap。

Owner：Ben

下一次 1-on-1 第一件事情不是：

> 「最近怎么样？」

而是：

> 「上一次我们说的三个 Action，现在怎么样？」

---

# Alex 最后形成自己的 1-on-1 Framework

每次 30–45 分钟。

不是机械地把五项全部问一次，而是快速 Scan，再深入最重要的部分。

---

# 1-on-1 Flow

## ① Check-in — 5 min

先了解人的状态。

「最近两星期怎么样？」

「有什么事情特别顺或者特别烦？」

目的不是 Small Talk。

而是寻找 Signal。

↓

## ② Performance — 5–10 min

讨论近期表现。

**Manager 看：**

Delivery
Quality
Ownership
Collaboration
Growth

重点：

> 找 Pattern，不是抓一次 Mistake。

↓

## ③ Career — 5–10 min

讨论：

**Career Direction**

↓

**Skill Gap**

↓

**Opportunity**

↓

**Development Action**

不要每一次都问 Career。

可以每月或每几次 1-on-1 深聊一次。

↓

## ④ Workload — 5–10 min

检查：

**Capacity**

**Priority**

**Context Switching**

**Hidden Work**

特别注意：

> 80% Planned Work + 20% Interrupt

通常比：

> 100% Planned Work

更现实。

↓

## ⑤ Problem — 10 min

寻找：

**Technical**

**Requirement**

**Process**

**People**

**Dependency**

**Management**

然后 Manager 判断：

> Developer 自己解决？

还是：

> Manager Remove Blocker？

↓

## ⑥ Action — 5 min

最后必须形成：

**Problem → Action → Owner → Due / Checkpoint**

---

# Alex 的 1-on-1 Note 最后变得非常简单

## Ben — 1-on-1

**Performance**

Delivery good.
Code Review slowing down due to workload.

**Career**

Interested in Solution Architecture.
Need Azure Architecture exposure.

**Workload**

Payment + Production + Mentoring = overload risk.

**Problem**

Requirement frequently changes after development starts.

**Manager Feedback**

Avoid committing deadlines before engineering estimation.

**Actions**

* Alex → Adjust Production Support rotation
* Alex → Add Ben to Azure Architecture discussion
* Ben → Prepare Payment architecture gaps
* Alex → Discuss requirement readiness with PO

---

# 但这里还有一个非常重要的管理原则

1-on-1 不是五个独立 Topic。

真正厉害的 SDM 会看到它们之间的因果关系。

例如：

```text
Performance Drop
      ↓
为什么？
      ↓
Workload Overload
      ↓
为什么？
      ↓
Senior Developer 承担太多 Support
      ↓
为什么？
      ↓
Junior Developer Skill 不足
      ↓
为什么？
      ↓
没有 Career / Development Plan
```

所以表面看到的是：

> **Ben Delivery 变慢。**

差的 Manager 会说：

> 「你需要 Improve Performance。」

好的 Manager 会继续追：

> **Why？**

最后发现真正的问题可能是：

**Team Capability + Workload Distribution + Priority Management。**

---

# SDM 最终要记住

一场好的 1-on-1，不是为了完成 Calendar 上的 Meeting。

而是持续回答五个问题：

### Performance

**这个人现在表现怎么样？为什么？**

### Career

**他未来想去哪里？我怎么帮助他成长？**

### Workload

**他的 Capacity 是否健康？**

### Problem

**什么东西正在阻碍他成功？**

### Action

**我作为 Manager 接下来要做什么？**

所以 Alex 后来不再用：

> 「Any problem？」

来结束 1-on-1。

而是用：

> **「有什么事情正在让你的工作变得比它应该有的更困难？」**

因为 Software Development Manager 的工作，不只是管理人的 Performance。

更重要的是：

> **创造一个让团队能够持续有 Performance 的环境。**
