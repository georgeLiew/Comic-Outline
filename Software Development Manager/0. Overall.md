# 《我不写 Code 以后，为什么反而更忙了？》

## Software Development Manager 实战漫画课程

# Chapter 1：星期一早上，所有东西都是 Priority

## 案例

星期一 9:05 AM。

Alex刚坐下来，Teams已经出现十几条信息。

**Product Owner：**

> 「Customer 要这个 Feature，这个月一定要上线。」

**Sales：**

> 「这个 Customer 很重要，可以先做吗？」

**Operation：**

> 「Production 昨天又有问题。」

**Developer：**

> 「上星期那个 Requirement 还没 Confirm。」

**老板：**

> 「Alex，Q3 Roadmap 为什么 Delay？」

Alex打开 Jira。

发现团队同时有：

* 3 个 Project
* 8 个 Feature
* 12 个 Bug
* 4 个 Production Issue
* 2 个 Technical Debt

每个人都说自己的事情最重要。

Alex突然发现：

> Software Development Manager 第一个工作不是「催 Developer」。

而是：

> **决定团队应该把时间花在哪里。**

## Alex 怎么处理

他没有马上问：

> 「谁可以做？」

而是先把所有工作分类：

| 类型                 | 例子                   |
| ------------------ | -------------------- |
| Production         | Payment Failure      |
| Committed Delivery | Customer Project     |
| Product Feature    | New Promotion Module |
| Technical Debt     | Upgrade .NET         |
| Improvement        | CI/CD Enhancement    |

然后建立 Priority Rule：

**P0 — Production Critical**

↓

**P1 — Contract / Committed Delivery**

↓

**P2 — Business Value Feature**

↓

**P3 — Improvement**

↓

**P4 — Technical Debt**

最后告诉 Stakeholder：

> 「不是我们不做，而是我们现在选择先做什么。」

---

## 本章最后才解释：Software Development Manager 的 Priority Management

Manager不是管理 Task。

Manager真正管理的是：

**Capacity × Priority × Business Value × Risk**

操作流程：

Business Request

↓

Understand Business Impact

↓

Estimate Effort

↓

Identify Dependency

↓

Identify Risk

↓

Compare Priority

↓

Allocate Team Capacity

↓

Commit Delivery

# Chapter 2：Business 连 Requirement 都没有，就问「要几个月？」

## 案例

Sales准备参加一个 Tender。

Tender要求开发一套新的 Transport Management System。

Sales问：

> 「Alex，这个 System 要多久？」

Alex：

> 「Requirement 呢？」

Sales：

> 「还没有。」

Alex：

> 「Business Flow？」

Sales：

> 「Customer 还没给。」

Alex：

> 「Integration？」

Sales：

> 「不确定。」

然后Sales问：

> 「那你可以给 Manday 吗？」

Alex第一次给：

> 120 Mandays。

Sales拿去报价。

两个月后Customer Requirement出来：

* Mobile App
* Payment Gateway
* ERP Integration
* Reporting
* Offline Mode
* Approval Workflow
* Notification
* Role Permission

Developer重新估：

> 280 Mandays。

老板问Alex：

> 「为什么差这么多？」

---

## Alex 学会了一个原则

**Unknown Requirement ≠ Detailed Estimation**

但Tender又不能回答：

> 「不知道。」

所以Alex改成：

### ROM Estimate

**Rough Order of Magnitude**

例如：

> Estimated Delivery: 6–9 months

并明确Assumption：

* Web System
* 1 Mobile App
* Existing Payment Gateway
* Maximum 3 External Integrations
* Standard Reporting
* No Offline Capability
* Existing Infrastructure

同时写：

> Estimate Confidence: ±40%

等Requirement越来越清楚：

Tender

→ ROM Estimate

→ Discovery

→ High Level Design

→ Feature Breakdown

→ Detailed Estimate

→ Delivery Baseline

---

## 本章最后才解释：Estimation Management

Software Development Manager不是负责「猜日期」。

而是管理：

> **Estimate Confidence**

操作过程：

Scope

↓

Assumption

↓

Dependency

↓

Complexity

↓

Risk

↓

Historical Velocity

↓

Buffer

↓

Estimate Range

不要说：

> 「需要6个月。」

应该说：

> 「根据目前Assumption，我们估计6–9个月；完成Discovery后可以缩小到±15%。」

# Chapter 3：Developer 说「Requirement 不清楚」

## 案例

PO建立一个 User Story：

> As a user, I want to cancel booking.

Developer问：

> 「Cancel以后Refund吗？」

PO：

> 「应该。」

Developer：

> 「Partial Refund呢？」

PO：

> 「要问Business。」

Developer：

> 「Payment Gateway已经Settlement怎么办？」

PO：

> 「不确定。」

Developer：

> 「Admin可以Override吗？」

PO：

> 「应该可以。」

Sprint已经开始三天。

Developer还没开始写Code。

Management却问：

> 「为什么Development这么慢？」

---

## Alex没有要求Developer「先做再说」

他暂停Development。

召开 Refinement。

把 Requirement 拆成：

### Business Rule

* 什么情况下可以Cancel？
* Departure前多久？
* 谁可以Cancel？

### Financial Rule

* Full Refund？
* Partial Refund？
* Cancellation Fee？

### Exception

* Payment Settled
* Trip Started
* Voucher Used
* Promo Code
* Partial Payment

### Permission

* Customer
* Counter
* Admin
* Supervisor

最后定义：

**Definition of Ready**

Story没有满足以下条件：

* Business Flow
* Acceptance Criteria
* Business Rules
* Exception Cases
* Dependency
* UI/UX
* API Impact

就不能进入Sprint。

## Incident处理

↓

Assess Severity

↓

Assign Incident Commander

↓

Mitigate

↓

Rollback / Fix

↓

Verify

↓

Communicate

↓

Postmortem

↓

Corrective Action

恢复以后才做：

### Root Cause Analysis

为什么Payment Failure？

因为Timeout。

为什么Timeout？

Database Query慢。

为什么Query慢？

Missing Index。

Staging Data太少。

没有Performance Test Dataset。

> Developer忘记Index。

> **Delivery Process没有Performance Validation。**

# Chapter 10：老板问「为什么Developer越来越多，Delivery没有越来越快？」

## 案例

以前：

5 Developers

→ 20 Features / Quarter

后来：

10 Developers

→ 27 Features / Quarter

老板：

> 「人数Double，为什么不是40？」

Alex开始分析。

发现Developer每天：

* Meeting：2小时
* Production Support：1小时
* Requirement Clarification：1小时
* Waiting Environment：0.5小时
* Coding：3.5小时

真正的问题不是：

> Developer不够。

而是：

> **Flow Efficiency太低。**

---

## Alex开始看Engineering Metrics

不是只看：

❌ Lines of Code

❌ Number of Tickets

❌ Developer Utilization 100%

而是：

* Lead Time
* Cycle Time
* Deployment Frequency
* Change Failure Rate
* MTTR
* Escaped Defect
* Rework Rate
* Blocked Time

例如：

Requirement

→ 3 Days Waiting

Development

→ 2 Days

QA

→ 4 Days Waiting

Testing

→ 1 Day

总Lead Time：

**10 Days**

真正Coding：

**2 Days**

所以问题不是Developer慢。

而是：

> **8天都在等待。**
