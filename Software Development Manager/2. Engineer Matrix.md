Chapter：老板问：“为什么这个 Team 越来越慢？”
案例：明明每天都很忙，为什么 Feature 就是出不来？

星期五 4:30 PM。

Alex 正准备关电脑，老板走过来。

老板：

“Alex，我感觉你的 Development Team 最近越来越慢。”

Alex愣了一下。

Alex：

“可是大家每天都很忙啊。”

老板打开 Roadmap：

Month	Planned Features	Delivered
May	8	7
June	8	6
July	8	4
August	8	3

老板问：

“所以问题在哪里？”

Alex第一反应是打开 Jira。

他发现：

Developer 每天都有 Ticket
Sprint 几乎都是满的
每个人都有 Commit
大家也经常加班
Daily Standup 每天都说 “In Progress”

可是……

Feature 就是越来越慢。

Alex突然意识到：

Busy ≠ Productive ≠ Delivering Value

这就是 SDM 为什么需要 Engineering Metrics。

1. Engineering Metrics 到底是什么？

Engineering Metrics 不是用来回答：

“哪个 Developer 最努力？”

而是回答：

“我们的 Software Delivery System 健不健康？”

一个 SDM 可以把 Engineering Metrics 分成五层：

Layer	SDM想知道什么？	Metrics
Delivery	东西出得快不快？	Lead Time, Cycle Time, Throughput
Flow	工作有没有卡住？	WIP, Flow Efficiency, Aging Work
Quality	出去后稳不稳定？	Defect Rate, Escaped Defects, Rework
Reliability	Deployment 安不安全？	Deployment Frequency, Change Failure Rate, MTTR
Predictability	我们讲的日期可信吗？	Planned vs Delivered, Carryover Rate

这五层一起看，才比较接近真实情况。

2. Alex 第一个看：Cycle Time

假设 Jira 有：

TASK-101
Start Development: Monday 10 AM
Done: Wednesday 10 AM

那么：

Cycle Time = 2 days

它回答：

“一件工作一旦真正开始，多久可以完成？”

Alex把过去几个月的数据拉出来：

Month	Median Cycle Time
May	3.2 days
June	4.1 days
July	6.8 days
August	9.4 days

这就很有意思了。

不是 Developer “看起来”变慢。

而是：

一张 Ticket 从开始做到完成，真的越来越久。

但这仍然没有回答：

为什么？

所以不能看到 Cycle Time 上升就马上 blame Developer。

3. Alex继续拆 Cycle Time

Alex抽出 TASK-382。

这个 Feature 总共花了 10天。

但仔细看：

Development       2 days
Waiting for PO    2 days
Development       1 day
Waiting for QA    3 days
QA                1 day
Bug Fix            1 day
------------------------
Total             10 days

真正 Coding：

3天

真正 QA：

1天

等待：

5天

Bug Fix：

1天

Alex发现：

Developer 根本不是主要问题。

真正的问题是 Waiting Time。

4. Flow Efficiency：真正工作的时间有多少？

这时候可以看：

Flow Efficiency = Active Time ÷ Total Cycle Time × 100%

刚才的例子：

Active Work = 5 days
Total Cycle Time = 10 days

所以：

Flow Efficiency = 50%

换句话说：

一张 Ticket 有一半时间不是在做，而是在等。

这对于 Manager 非常重要。

因为如果你只告诉 Developer：

“大家做快一点。”

即使 Coding 快 20%，整体 Delivery 可能只改善一点点。

但是如果你解决：

Waiting for PO
Waiting for QA
Waiting for Environment
Waiting for Code Review
Waiting for Approval

Cycle Time 可能直接大幅下降。

5. 第二个问题：WIP 太高

Alex再看 Team Board。

发现7个 Developer：

Developer A → 3 Tasks
Developer B → 4 Tasks
Developer C → 2 Tasks
Developer D → 5 Tasks
Developer E → 3 Tasks
Developer F → 4 Tasks
Developer G → 3 Tasks

总共有：

24个 In Progress

Alex以前觉得：

“很好，每个人都有很多事情做。”

其实这是危险信号。

因为大量 WIP（Work In Progress）通常意味着：

Task A
 ↓
做到一半
 ↓
Requirement 问题
 ↓
先做 Task B
 ↓
Production Issue
 ↓
去 Fix Production
 ↓
回来忘记 Task B
 ↓
重新理解
 ↓
继续 Task A

大量 Context Switching 开始出现。

所以：

高 Utilization 不一定等于高 Throughput。

6. Throughput：团队真正完成多少东西？

Alex开始看每周完成数量。

Week	Completed Work Items
W1	18
W2	17
W3	14
W4	11
W5	9

这叫 Throughput。

它回答：

“一个时间周期内，团队真正完成多少 Work Items？”

这里又看到明显趋势：

18 → 17 → 14 → 11 → 9

Delivery capacity 正在下降。

但是 Alex 仍然不能马上说：

“Developer performance dropped.”

因为可能是：

Ticket 变大
Production Issue 增加
Requirement 不清
QA bottleneck
Technical Debt
Code Review 慢
Dependency 增加

Engineering Metrics 的重点就是：

发现问题 → Drill Down → 找原因

而不是：

Metric 下降 → 找人负责

7. Alex发现第三个问题：Rework

Alex继续看 August。

团队完成了 40 张 Ticket。

表面看不错。

但是：

40 Completed


↓ Production


12 reopened
8 bug fixes
5 hotfixes

原来很多 Engineering Capacity 被拿去 修之前做过的东西。

这时候可以看 Rework Rate。

例如：

Total Completed Work = 40
Rework-related Work = 10

那么大约：

25% 的工作量正在 Rework。

这代表每4份 capacity，大约1份不是创造新的 Business Value，而是在修过去的问题。

8. Quality Metrics 开始出现

Alex建立：

Metric	July	August
Bugs Found in QA	18	27
Production Bugs	4	11
Reopened Tickets	6	12
Hotfixes	2	7

真正危险的不是 Bug 总数本身。

而是趋势：

Production Defect ↑
Reopen ↑
Hotfix ↑

这可能意味着：

团队为了赶 Delivery，开始牺牲 Quality。

然后形成恶性循环：

Deadline Pressure
       ↓
Rush Development
       ↓
More Bugs
       ↓
More Production Issues
       ↓
More Rework
       ↓
Less Capacity
       ↓
Feature Delay
       ↓
More Deadline Pressure

这才是 SDM 应该解决的东西。

9. Deployment Metrics：团队敢不敢 Release？

Alex又发现一个现象。

以前 Team：

Release
Mon
Wed
Fri

现在：

“大 Feature 做完才一起 Release。”

于是每两三个星期才 Deployment 一次。

Deployment 越来越大：

Feature A
Feature B
Feature C
DB Migration
Config Change
Bug Fix

全部绑在一起。

风险自然越来越高。

这时候可以参考常见的 DORA Metrics：

Metric	问的问题
Deployment Frequency	多久 deploy 一次？
Lead Time for Changes	Change 多久可以到 Production？
Change Failure Rate	Deployment 有多少导致问题？
MTTR	出问题多久恢复？

例如：

20 deployments/month


4 caused incidents

那么：

Change Failure Rate = 20%

如果 Production 出问题平均：

Detection → Recovery = 3.5 hours

那么 MTTR（Mean Time to Recovery）大约：

3.5 hours

10. Predictability：SDM最应该关心的 Metric 之一

老板真正关心的通常不是：

“Developer 每天写多少 Story Point？”

而是：

“你说月底上线，到底能不能上线？”

所以 Alex 开始记录：

Sprint	Planned	Delivered	Carryover
21	20	18	2
22	20	16	4
23	20	13	7
24	20	11	9

Carryover 越来越严重。

代表：

Sprint Planning
      ↓
Commit 20
      ↓
Complete 11
      ↓
9 move next sprint
      ↓
Next Sprint + New Work
      ↓
WIP increases
      ↓
Delivery slows

这说明团队已经出现 Predictability Problem。

11. 一个 SDM Dashboard 可以长这样

Alex最后没有建立一个“Developer排行榜”。

而是建立一个 Engineering Health Dashboard：

Category	Metric	Current	Trend
Delivery	Median Cycle Time	9.4 days	↑
Delivery	Weekly Throughput	9	↓
Flow	WIP	24	↑
Flow	Flow Efficiency	50%	↓
Quality	Production Defects	11	↑
Quality	Rework Rate	25%	↑
Reliability	Deployment Frequency	2/month	↓
Reliability	Change Failure Rate	20%	↑
Reliability	MTTR	3.5 hrs	↑
Predictability	Sprint Carryover	45%	↑

现在 Alex终于可以回答老板：

“Team 不是单纯 Developer 写 Code 变慢。”

“我们的 Cycle Time 从 3.2 天升到 9.4 天。主要原因是 WIP 增加、QA/Requirement waiting time，以及 Production Rework。”

“目前约 25% capacity 被 Rework 吃掉，所以 Feature Throughput 才一直下降。”

这就是 Manager-level conversation。

12. 接下来不是催人，而是做 Action

Alex针对 Metrics 做不同动作：

Signal	Manager Action
Cycle Time ↑	找哪个 stage 最慢
WIP ↑	设置 WIP Limit
Waiting Time ↑	找 bottleneck / dependency
QA Queue ↑	调整 Dev/QA workflow
Rework ↑	Root Cause Analysis
Production Defect ↑	加强 test / review / release gate
Deployment Frequency ↓	改善 CI/CD
Change Failure Rate ↑	Smaller deployment + automated testing
MTTR ↑	Monitoring / rollback / runbook
Carryover ↑	改善 estimation / refinement / scope control

所以 Engineering Metrics 最终一定要形成：

Metric → Signal → Diagnosis → Action → Observe

而不是：

Metric → Report → PowerPoint → End

13. 千万不要把 Engineering Metrics 变成员工 KPI

这是 SDM 很容易踩的坑。

例如：

Developer A
Commits: 72


Developer B
Commits: 31

不能因此说：

Developer A 比 Developer B productivity 高两倍。

因为 B 可能：

做 architecture
Review PR
带 Junior
Debug production
解决复杂问题
一个 Commit 就解决核心问题

同样：

Lines of Code
Number of Commits
Number of Tickets
Story Points per Developer
PR Count

都非常容易被 Gaming。

一旦 Developer 知道：

“Ticket 数量 = Performance”

自然会发生：

一个 Feature


以前：
1 Ticket


现在：
8 Tickets

Dashboard 变漂亮了。

Software 没有变快。

14. Engineering Metrics 应该看 Team，不是看人

比较健康的层级是：

Business
   ↓
Are we delivering value?


Product
   ↓
Are features delivered predictably?


Engineering
   ↓
Is work flowing efficiently?


Quality
   ↓
Are we creating rework?


Operations
   ↓
Can we deploy and recover safely?

所以 SDM 真正想建立的是一个因果链：

WIP ↑
 ↓
Waiting ↑
 ↓
Cycle Time ↑
 ↓
Throughput ↓
 ↓
Feature Delivery ↓
 ↓
Roadmap Delay ↑
 ↓
Business Value delayed

这样 Engineering Metrics 才和 Business Value 接起来。

15. 回到这个 Chapter 的结局

一个月后。

Alex再次进入 Management Meeting。

老板问：

“Development performance 怎样？”

Alex没有再说：

“大家最近都很努力。”

而是打开 Dashboard：

WIP
24 → 13


Median Cycle Time
9.4 days → 5.8 days


Rework
25% → 14%


Production Defects
11 → 6


Weekly Throughput
9 → 14

Alex说：

“我们没有要求 Developer 加班。”

“我们减少了同时进行的工作、缩短 QA Queue，并处理了最主要的 Rework source。”

“所以 Cycle Time 已经下降约 38%，Throughput 也开始恢复。”

老板点头。

因为这一次 Alex 管理的已经不只是 Developer。

他管理的是：

Engineering System。

SDM 最后要记住的 Engineering Metrics 思维

不要问：

“Developer 有没有很忙？”

要问：

“Work 有没有顺畅地从 Requirement 流到 Production？”

也不要追求某一个 Metric 越高越好。

Engineering Metrics 更像汽车 Dashboard：

Cycle Time 告诉你速度，WIP 告诉你是不是塞车，Defect/Rework 告诉你是不是一直返工，DORA Metrics 告诉你 Release Engine 健不健康，而 Predictability 最终告诉 Business：

“这个 Engineering Team 说要交付的东西，到底有多可信。”
